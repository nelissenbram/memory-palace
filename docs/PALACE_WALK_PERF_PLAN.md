## Synthesis plan (verbatim)

```
ROOT-CAUSE NARRATIVE
=====================

The symptom is two stacked problems plus a desktop-specific multiplier. All fixes below are timing/reuse/orchestration only — zero visual change.

MECHANISM 1 — Open-loop transition choreography (dominant cause of "slow to move between palace parts", all platforms).
Every door click pays a fixed ~2.1–2.5s regardless of actual readiness: `palaceStore.ts:72-80 fade()` holds the view swap behind a hardcoded 500ms setTimeout (so the new scene cannot even START mounting until the fade ends — work serialized after the sleep), then `MemoryPalace.tsx:470-484` shows PalaceLoadingScreen dismissed by a fixed `setTimeout(2000)` for all 8 intra-palace view pairs. No readiness signal exists: `onReady` is wired only for ExteriorScene (ExteriorScene.tsx:31/3064 → MemoryPalace.tsx:922); EntranceHall/Corridor/Interior expose none. Since scenePreloader already pre-warms the JS chunks, most of the 2.5s is pure dead time. Walking exterior→entrance→corridor→room = 3 doors ≈ 6–7s of loading cards. This is worst on FAST desktops: the scene mounts in a few hundred ms and the rest of the timer covers nothing.

MECHANISM 2 — Full teardown + rebuild of every scene on every hop, with shader-program flush; amplified by an EntranceHall remount bug.
Only ExteriorScene persists (body portal, MemoryPalace.tsx:601-621); Entrance/Corridor/Interior mount conditionally on `view` (MemoryPalace.tsx:1044-1046) and their unmount cleanups dispose EVERY material (CorridorScene.tsx:1594-1606, EntranceHallScene.tsx:2334-2346, InteriorScene.tsx:~2280). material.dispose() drops three.js program refcounts to zero, so the renderer pool (rendererPool.ts, whose own comment cites 50–200ms/scene compile cost) saves only context creation — every transition still recompiles the full shader set, re-runs PMREM (assetLoader.ts:127-136 re-runs fromEquirectangular even for cached HDR data), rebakes two 2048² shadow maps, and rebuilds a 1500–2300-line scene graph synchronously on the main thread, in BOTH directions.
Amplifier: EntranceHallScene's entire construction effect deps on `[wingsProp]` (EntranceHallScene.tsx:2358), but `useNavigation.ts:23` calls `getWings()` every render and roomStore.ts:138-142 returns a fresh array each call. Every MemoryPalace re-render while in the hall = full teardown+rebuild + camera teleport to spawn. The transition path itself guarantees 1–2 wasted full hall rebuilds per door click (setSceneLoading true→false, corridorPaintings effect at MemoryPalace.tsx:795-798), and any store update mid-walk (toasts, polling) causes a multi-hundred-ms freeze + teleport in the hub scene.

MECHANISM 3 — Desktop pays structurally more than the native apps, with no capability check.
(a) Tier assignment is blind: getGPUTier (mobilePerf.ts:41-67) forces Capacitor apps to the cheap mobile tier, but the desktop branch never runs detectRendererString — the potato patterns that explicitly list SwiftShader/llvmpipe/Intel HD (mobilePerf.ts:17-25) are dead code on desktop. Any desktop, including software-rendered Chrome, gets DPR 2, SSAO+NormalPass (scene rendered twice), Bloom, SMAA, 2048 PCFSoft shadows, MeshPhysicalMaterial everywhere, dozens of extra lights. So every rebuild/recompile from Mechanism 2 is far heavier on desktop (Windows ANGLE/D3D shader translation compounds it) — this is why desktop feels worse than the WebView apps.
(b) Desktop-only frame taxes: per-mousemove hover raycasts with no guard (EntranceHallScene.tsx:2110-2148, InteriorScene.tsx:2132-2156 — Corridor has the intended 3px guard at 1497); dt-independent camera lerps (`pos.lerp(posT,.1)`, CorridorScene.tsx:1454/1365 + same in the other scenes) that turn any fps deficit into rubber-band input lag; the hidden ExteriorScene rAF loop doing all its CPU animation work before the paused check at ExteriorScene.tsx:3062.

MECHANISM 4 — Redundant asset work landing on the hot path.
PBR cache keyed by repeat value (assetLoader.ts:293): the same 4 JPGs decode+upload up to 6× (exterior loads plaster at 5 repeats, ExteriorScene.tsx:216-227), and preloadSharedAssets warms repeats no scene requests. Corridor paintings load full-res originals via a fresh uncached TextureLoader mid-walk (CorridorScene.tsx:601-610) and the corridor double-mounts per entry because its React key includes `JSON.stringify(corridorPaintings)` which populates async. Room photos all route through `?stream=1` → Vercel function doing auth + up to 4 DB queries per image instead of the 302-to-Cloudflare path (route.ts:150-155, textureHelpers.ts:96-98).
```
