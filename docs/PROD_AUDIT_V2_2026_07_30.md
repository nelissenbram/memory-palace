## P0 — confirmed

### [Library/functionality] Bulk "Move" silently moves only the first selected memory
- file: `src/components/ui/RoomMediaPanel.tsx`
- In select mode the user can multi-select memories and taps the "Move" (moveSelected) action. handleMoveSelected takes ONLY the first id from the selection set, opens the move dialog for that single mem, and immediately clears the whole selection. When the user then picks a destination room, only that one memory moves; every other selected memory is left behind with no indication. The button label in several locales is even "Move to room", strongly implying a batch move. This is a data-affecting mis-wired control: the user believes N items moved when only 1 did.
- fix: Carry the full selection into the move flow (store movingMems: Mem[] instead of a single movingMem), and in handleMoveToRoom iterate the set calling moveMemory(room.id, targetRoomId, id) for each. Only clear selectedIds after the dialog resolves, not before, so a cancelled dialog does not discard the selection.

### [Interview/functionality] AI follow-up flag corrupts nextQuestion(): user is stuck re-answering the same question after every AI response
- file: `C:\Users\nelis\memory-palace-staging\src\lib\stores\interviewStore.ts`
- saveCurrentResponse() on the AI-success path passes aiData with a followUp, and the store sets isFollowUp:true (interviewStore line 240: `isFollowUp: !!aiData?.followUp`). The AI route ALWAYS returns a followUp (route.ts line 118), so isFollowUp becomes true after essentially every answered question. When the user then taps Continue, handleContinue() calls nextQuestion() for any non-last question. But nextQuestion() (interviewStore line 205) branches on isFollowUp and, when true, sets `isFollowUp:false` WITHOUT incrementing currentQuestionIndex. Result: the panel re-renders the SAME question (and the progress bar never advances). The follow-up feature is only half-wired — answerFollowUp() is never called and isFollowUp is never read in InterviewPanel (it is destructured on line 84 but unused), so the flag has no legitimate consumer and only corrupts progression.
- fix: The panel does not implement a follow-up question turn, so nextQuestion() must always advance. Either stop setting isFollowUp in saveCurrentResponse (pass no follow-up flag), or make nextQuestion() unconditionally do `set({ currentQuestionIndex: currentQuestionIndex + 1, isFollowUp: false, transcript: "" })`. Verify progress advances across all questions after an AI reply.

### [Backend/security+data] Passcode column is readable by any anonymous client via RLS — passcode protection is fully bypassable
- file: `C:\Users\nelis\memory-palace-staging\supabase\migrations\011_public_shares.sql`
- public_shares RLS policy 'Anyone can read active public shares' is `for select using (is_active = true)` with no column restriction. Migration 012 adds the plaintext `passcode` column to this same table and relies on that policy. The public route connects with the ANON key. Any unauthenticated client using the anon key can `select passcode, slug from public_shares where is_active` and read every active passcode in plaintext plus every slug, defeating the passcode mechanism entirely and enabling direct fetch of protected content.
- fix: Never expose passcode/created_by via anon SELECT. Drop the anon SELECT policy and serve all public/passcode reads through the server route using the service-role client selecting only non-secret columns; or replace the broad policy with a security-barrier view exposing only id/slug/room_id/wing_id/is_active/expires_at/scope. Also hash the stored passcode (sha256) so a leak does not reveal cleartext.

### [Backend/security+data] Public route serves passcode-scoped shares with no passcode/scope check — knowing the slug bypasses the passcode
- file: `C:\Users\nelis\memory-palace-staging\src\app\api\public-share\[slug]\route.ts`
- GET /api/public-share/[slug] selects a share by `slug` + `is_active=true` only. It never checks `scope` and never requires the passcode. Rows created by createPasscode have scope='passcode' and a passcode, but this route returns their full room/wing memories to anyone with the slug. Combined with the anon-readable slug (finding above) and validatePasscode returning the slug to the browser, the passcode gate is decorative — a passcode-protected wing/room is effectively fully public.
- fix: Gate this route by scope: for scope='passcode' shares require a validated passcode (a signed short-lived token from validatePasscode, or re-verify a supplied passcode against the hashed value) before returning memories. Exclude scope='passcode' rows from the plain slug path (`.eq('scope','view')`) unless an authorization token is supplied.

### [Backend/security+data] getPublishedMemories / getPublishedRooms are public server actions that read via the admin client with NO published_at gate (unauthenticated IDOR read of private memories)
- file: `src/lib/social/visit-actions.ts:82-164 (getPublishedRooms), 179-209 (getPublishedMemories)`
- visit-actions.ts is a `"use server"` module, so every export is an independently POST-invokable endpoint. getPublishedMemories(roomId) queries with createAdminClient() (RLS bypassed) filtering ONLY by room_id + displayed!=false — no wing-published check, no auth, no ownership binding. getPublishedRooms(wingId) fetches the wing but never inspects published_at. The page-level guards live in the PAGE, not the action, and are bypassed on direct invocation. Anyone who knows or guesses a room UUID can read memory titles, descriptions and file_urls of unpublished/unpublished-again wings; real room UUIDs are handed to every visitor via getPublishedRooms().id.
- fix: Move the publish/authorization gate into the actions: in getPublishedMemories resolve rooms.wing_id and require wings.published_at IS NOT NULL; in getPublishedRooms early-return [] when wing.published_at is null. Better, convert these cross-user readers to non-action internal helpers (a file WITHOUT `"use server"`) imported only by the verified page.

### [Backend/security+data] IDOR: verify-receipt links ANY valid Apple receipt to the caller with no ownership check on original_transaction_id (entitlement theft + duplicate rows)
- file: `src/app/api/apple/verify-receipt/route.ts:124-137`
- POST /api/apple/verify-receipt takes an attacker-supplied receipt, asks Apple to validate it, and on status 0 upserts plan=guardian/keeper onto the CALLING user's row. There is no check that activeReceipt.original_transaction_id is already linked to another user, and migration 20260614_apple_iap.sql only creates a non-unique index on apple_original_transaction_id. User B who obtains User A's valid receipt (family sharing, leaked/instrumented device) POSTs it and gets plan=guardian linked to A's transaction — two accounts entitled from one purchase. getUserPlan honors it everywhere; the webhook's .maybeSingle() lookup then breaks with two rows sharing the id.
- fix: Before upserting, query for any OTHER user already holding this original_transaction_id (`.eq('apple_original_transaction_id', otxid).neq('user_id', user.id).maybeSingle()`) and reject 409 if found. Add a partial UNIQUE index `create unique index ... on subscriptions(apple_original_transaction_id) where apple_original_transaction_id is not null` so the DB enforces one-transaction-per-user.

### [Backend/security+data] IDOR: ai-label reads ANY user's private memory image from storage, bypassing the /api/media ownership checks
- file: `C:\Users\nelis\memory-palace-staging\src\app\api\ai-label\route.ts`
- When imageUrl starts with '/api/media/', ai-label strips the prefix and downloads directly from storage — r2Download() uses full R2/S3 credentials with no per-user scoping — and never re-implements the ownership/share/published-wing authorization the real /api/media route performs. Storage paths are {bucket}/{user_id}/{filename}. An authenticated user with AI consent can POST { imageUrl: '/api/media/memories/<victim-user-id>/<file>' } and receive an AI description + labels of another user's private image. The bucket segment is also attacker-controlled and cast to "memories"|"busts" without validation.
- fix: Do not download by raw path. Look up the memory row and verify authorization exactly as /api/media does (memory.user_id === user.id, or accepted room_share, or published wing) BEFORE downloading. Validate bucket is exactly 'memories' and reject '..'/backslash/null segments (reuse isPathSafe). Factor the media route's authorize-then-fetch into a shared helper and call it here.

### [Backend/security+data] Self-notifications (milestones, achievements, first-in-room, family-joined) are silently blocked by RLS and never persist
- file: `src/lib/auth/notification-actions.ts:158-171 with supabase/migrations/035_fix_notifications_rls.sql:8-10`
- Migration 035 set the INSERT policy to `WITH CHECK (from_user_id = auth.uid())`. But createNotification() defaults from_user_id to null, and self-notification callers (checkAndNotifyMilestone, notifyFirstInRoom, notifyFamilyJoined) pass no fromUserId. The insert uses the RLS-bound anon client, so `null = auth.uid()` is false and every row is rejected. The rejection is swallowed by a surrounding `try { } catch { }`, so callers see success. No milestone/achievement/first-in-room/family-joined notification is ever written to the DB — the in-app Activity feed silently loses every self-generated notification.
- fix: For self-notifications (from_user_id null) and cross-user fan-out, insert via the service-role client instead of the RLS anon client, OR add a policy branch permitting `user_id = auth.uid()` for self-targeted rows. Stop swallowing the insert error — capture and console.error it so this failure mode is observable.

### [Backend/security+data] Referral reward mint is racy and non-idempotent — duplicate Stripe coupons (real money) per referral
- file: `src/app/api/referral/route.ts`
- POST /api/referral does a read-modify-write with no atomicity or unique guard: reads referred_by and returns early if set, then later writes referred_by, increments the referrer's count from a stale read, and mints a real Stripe coupon (amount_off:2499) + promotion code. Two concurrent POSTs — trivially triggered since register fires this best-effort after signup and clients retry — both pass the !referred_by check, so BOTH mint a coupon and BOTH increment. The count increment and the referral_rewards array append are additional lost-update races. Result: multiple 1-free-month Guardian coupons from a single referral, no Stripe idempotency key.
- fix: Make the write the gate: conditional UPDATE that only sets referred_by when currently NULL and check rowCount (`.update({referred_by:code}).eq('id',user.id).is('referred_by',null).select()`), aborting if 0 rows, and mint the coupon only after that update wins. Pass a deterministic Stripe idempotencyKey (`referral_${user.id}`). Increment referral_count via atomic SQL and append referral_rewards via jsonb append server-side.
