## (B) Weekly report — "This Week in Your Palace"

**Thesis:** a weekly must be parsed in 3 seconds. One hero, one CTA. Only reaches users active in the last 7 days (§E), so no "quiet week to everyone" spray.

### Final section set

| Section | Verdict |
|---|---|
| Header: wordmark + gold wing-seal, warm greeting + first name | **Keep** |
| **THE HERO** (pick ONE, priority order): On This Day → Shared-room activity → Upcoming time capsule | **Keep — the whole email** |
| Weekly stat line — single quiet line ("3 memories in 2 rooms this week"), NOT a tile grid | **Trim to one line** |
| **Streak block** (🔥 flame, "keep momentum", "finish line") | **CUT entirely** |
| **Track progress bar** | **CUT from weekly** (moved to monthly) |
| Single ember CTA | **Keep** |
| Footer: tagline, visible unsubscribe, legal | **Keep** |
| Quiet-week fallback body | **Effectively gone** — active-but-empty users get a one-line "quiet week" note; genuinely-no-content users are **suppressed** (§E content-gate) |

Hero priority: **On This Day** (nostalgia, gold frame, most on-brand) → **Shared activity** ("Maria added 2 memories to Nonna's Kitchen") → **Time capsule** ("A capsule opens Thursday"). The single stat line sits under the hero as quiet context.

### Subjects (rotate by hero, most-specific-true wins)

- OTD: **"On this day: {memoryTitle}"** · preheader *"A memory from {yearsAgo} years ago, still kept."*
- Shared: **"{contributorName} added to {roomName}"** · preheader *"Someone you share a room with left something new."*
- Capsule: **"A time capsule opens this week"** · preheader *"Something you sealed is almost ready."*
- Quiet: **"Your week in the palace"** · preheader *"A quiet look back at what you added."*

Never: "Weekly Digest", streak-in-subject, emoji.

### Body voice (before → after)

- Streak — *before:* "🔥 4 weeks in a row! Keep the momentum going!" → *after (only if streak ≥ 3, as one calm line):* "You've returned to your palace four weeks running. A habit worth keeping."

- CTA: **"Visit your palace"** (or **"Add this memory"** when hero is an OTD resurface).

## (D) 30-day win-back — the single knock, then stop

The calmest send. No guilt, no "we miss you!!", no discount-bait. Rides `send-reminder.ts` (`type: "re_engagement"`), restyled to the §A tokens.

- **Subject:** "Your palace is still here" · **preheader:** "Everything you kept is exactly where you left it."
- **Body:**
  > {firstName},
  >
  > It's been about a month — that's alright, the palace doesn't go anywhere. Everything you built is still standing: **{memoryCount} memories** across your wings, each one right where you left it. Whenever you're ready, there's a door.
  >
  > [ Walk back in ]
  >
  > *If you'd rather not hear from us, you can unsubscribe below — no hard feelings.*
- **CTA:** "Walk back in." Win-back names unsubscribe **in the body** (highest annoyance risk → easiest exit protects deliverability).

### Rules

- Eligible iff ALL: `email_digest !== false`; `winback_sent_at IS NULL`; `last_seen_at` between `now()-31d` and `now()-30d`; **no** memory `created_at >= now()-30d`.
- On send: **stamp `winback_sent_at = now()`** (mirrors the proven `welcome_email_sent_at` idempotency pattern).
- **"Then stop" is enforced by the marker**, not by day-bucketing alone. Clear `winback_sent_at` in `heartbeat-action.ts` on return (alongside the existing legacy-status reset) so a user who returns, re-lapses, and drifts again can get **one fresh** win-back per silence cycle — never two in a row.
- This **replaces** the drip cron's 14d + 30d re-engagement emails (§E).

## (E) Cadence & eligibility engine

**Core move:** periodic reports target the **active** cohort; win-back targets the **silent** cohort. They are disjoint by construction — a user cannot be both active-in-period and 30-days-silent — so a report and a win-back can never fire for the same user in the same run. The send-ledger is the belt-and-suspenders on top.

### Activity signal

**Active-in-period** = `profiles.last_seen_at >= windowStart` **OR** `EXISTS(memory WHERE user_id=? AND created_at >= windowStart)`. Memories is the true creation signal (indexed `idx_memories_user_created`); `last_seen_at` catches viewers. **Caveat:** `last_seen_at` is a palace-visit proxy written once/session on 3D mount — the OR-with-memory mitigates but doesn't fully cover Library/Atrium-only users; accept this as a known limitation.

### New infrastructure (build first)

1. **Migration** `supabase/migrations/<ts>_lifecycle_email.sql`:
   ```sql
   ALTER TABLE profiles
     ADD COLUMN IF NOT EXISTS monthly_highlights boolean DEFAULT true,
     ADD COLUMN IF NOT EXISTS family_updates_email boolean DEFAULT true,
     ADD COLUMN IF NOT EXISTS winback_sent_at timestamptz;
   CREATE TABLE IF NOT EXISTS email_send_log (
     user_id uuid NOT NULL,
     email_type text NOT NULL,   -- 'weekly' | 'monthly' | 'winback'
     sent_at timestamptz NOT NULL DEFAULT now()
   );
   CREATE INDEX IF NOT EXISTS idx_email_send_log_user ON email_send_log(user_id, sent_at DESC);
   ```
   `monthly_highlights`/`family_updates_email` are **read by the settings UI but have no migration today** — this is a hard prerequisite; the monthly gate is dead until it ships.

### Weekly — cron `15 9 * * 1` (Mon 09:15 UTC), route `/api/email/digest` (re-enabled)

Eligible iff ALL:
1. `email_digest !== false` (strict).
2. `created_at` > 7 days ago.
3. **Active in previous 7 days** (new gate — replaces the old "everyone not-active-today" spray).
4. **Has real content** (OTD / shared / capsule) OR active-but-quiet → one-line note; else **suppress**.
5. Has an auth email.
6. **Ledger:** no `weekly`/`monthly`/`winback` row in `email_send_log` for this user in the last 6 days.

On send: insert `email_send_log(user_id,'weekly')`.

### Monthly — cron `20 9 1 * *` (1st, 09:20 UTC), new route `/api/email/monthly`

Eligible iff ALL:
1. `email_digest !== false` **AND** `monthly_highlights !== false`.
2. `created_at` > 30 days ago.
3. **Active in previous ~30 days.**
4. ≥1 memory in the month (no memories → no chapter).
5. Has an auth email.
6. **Ledger:** no lifecycle row in the last 6 days (guards the 1st-of-month-lands-on-Monday collision → weekly is skipped that week for that user).

On send: insert `email_send_log(user_id,'monthly')`.

> Note: monthly does **not** exclude weekly-active users (rank-2's "not-active-this-week" split was rejected — it denies the most re-open-worthy retrospective/anniversary content to your best users). Overlap is instead handled by the ledger's 6-day cap, so an active user gets the monthly and simply skips that week's weekly.

### Win-back — folded into `/api/cron/drip-and-reengage` (daily 09:30)

**Mandatory reconciliation of the existing cron** (today `reengageDays=[7,14,30]` sends emails at *both* 14d and 30d + a 7d push → violates "exactly one"):
1. `reengageDays = [7, 30]`. Keep **7d = push only**. **Delete the 14d email.**
2. 30d tier becomes *the* win-back: gate on `winback_sent_at IS NULL`, send, stamp the marker. Add `winback_sent_at` to the route's `profiles` select.
3. Ledger: insert `email_send_log(user_id,'winback')`.

Net inactive-user timeline: push @7d → **one** win-back email @~30d → silence.

### Frequency caps & de-dupe (summary)

- **Structural:** active vs 30d-silent cohorts are disjoint → reports and win-back never collide per-run.
- **Ledger cap:** ≤ 1 lifecycle email (weekly/monthly/winback) per user per rolling 6 days. Onboarding drip (days 1–14) is exempt and already excluded from reports by the >7d account-age gate.
- **Distinct cron minutes:** push :00, weekly Mon :15, monthly 1st :20, drip/win-back :30 — no simultaneous runs; each route keeps `MAX_EMAILS_PER_RUN` (100) + the 50s-of-60s timeout guard.
- **Race note:** the ledger check-then-send is not transactional across cron runs, but distinct minutes + disjoint cohorts + the 6-day window make double-sends effectively impossible; if hardened later, use an `INSERT ... ON CONFLICT` unique key on `(user_id, email_type, date_trunc('week', sent_at))`.

### Prefs / unsubscribe / native

- **Gates:** weekly → `email_digest`; monthly → `monthly_highlights` AND `email_digest`; win-back → `email_digest`. All strict `=== false` (null/undefined = subscribed).
- **Headers:** every send emits `List-Unsubscribe` + `List-Unsubscribe-Post: One-Click` (reuse the existing block; `sendEmail` only forwards caller `headers`) **and** a visible footer link. Token = HMAC `signUnsubscribeToken(userId)` (no raw UUID — IDOR guard).
- **Scoped unsubscribe:** extend `/api/email/unsubscribe` to read `&scope=monthly` → flip only `monthly_highlights`; default/no-scope → `email_digest=false` (kill-all, backward compatible). **Fix the hardcoded confirmation copy** ("weekly digest emails", `unsubscribe/route.ts:155`) → report-neutral: *"You'll no longer receive Memory Palace update emails."* / scope-aware "monthly highlights" variant.
- **Native/iOS:** no email suppression needed or added — email ≠ push, no IAP/steering surface; the settings Email section is already always shown. Nothing to change.

### i18n

Fill **en, nl, de, es, fr** for every new key. Use the **key-first `map[key][locale]` + `r(key, locale)`** convention from `send-reminder.ts` (the cleanest of the three). New `send-monthly.ts` gets its own key-first `mt` map; win-back keys extend `send-reminder.ts`'s `rt`. Do **not** route email copy through `src/messages/*.json` (that's the client flat-lookup system; email never reads it for copy).

## (F) Deactivation-risk avoidance

The pause was **explicitly temporary, owner-requested** (commit `87fe9cc`), with re-enable baked in (restore the cron + redeploy). There is **no documented technical/deliverability/spam failure** to repeat — the anti-spam requirement is forward-looking. Concretely, this design avoids re-earning a pause by:

1. **No blast.** Reports reach only active-in-previous-period users; the old "everyone not-active-today" spray (which mailed dormant users empty digests) is gone.
2. **No empty sends.** The content-gate suppresses contentless weeklies — no manufactured filler.
3. **Fewer emails than today.** The 14d re-engagement email is deleted; disengaged users go from two nags to one calm knock.
4. **Hard ceiling.** Ledger enforces ≤1 lifecycle email / 6 days; monthly-on-the-1st auto-skips that week's weekly.
5. **No dark patterns.** Streak flames, loss-framing, countdowns, leaderboards, fake scarcity, guilt copy all cut — retention rests on nostalgia + genuine utility + one calm CTA.
6. **Frictionless, honest exit.** One-click headers + visible link + scoped monthly opt-out (drop monthly without losing weekly) → users tune instead of nuking, lowering complaint rate and protecting deliverability.
7. **Deliverability hygiene preserved.** Correct `from`/`reply_to`, plain-text fallback, per-type tags, List-Unsubscribe one-click — all already in the pipeline, all kept.

**Per-user footprint:** highly-active ≈ 4 weeklies/month + 1 monthly (that week's weekly suppressed) → ~4/mo; lightly-active → 1–2/mo; gone-silent → 1 push @7d + 1 win-back @~30d, then 0.

```typescript
/** key-first lookup with English fallback (mirrors send-reminder.ts's r()) */

  const row = mt[key];
  if (!row) return key;
  return row[locale] || row.en;

const DATE_LOCALE: Record<string, string> = { en: "en-US", nl: "nl-NL", de: "de-DE", es: "es-ES", fr: "fr-FR" };

function monthName(monthDate: string | undefined, locale: string): string {
  const dl = DATE_LOCALE[locale] || "en-US";
  const d = monthDate ? new Date(monthDate) : new Date();
  const name = d.toLocaleDateString(dl, { month: "long" });
  return name.charAt(0).toUpperCase() + name.slice(1); // capitalize (nl/de/es/fr months often lowercase)
}
```

## THE SEND-LEDGER HELPER (shared de-dupe surface)

```ts
// src/lib/email/send-ledger.ts  (new)
import type { SupabaseClient } from "@supabase/supabase-js";

export type LifecycleEmailType = "weekly" | "monthly" | "winback";

/** Rolling window (days) for the "≤1 lifecycle email per user" ceiling. */
export const LEDGER_WINDOW_DAYS = 6;

/**
 * Returns the Set of user IDs (from `candidateIds`) who have received ANY
 * lifecycle email (weekly | monthly | winback) within the last
 * LEDGER_WINDOW_DAYS. These users are barred from another lifecycle send
 * this run — the belt-and-suspenders on top of disjoint cohorts.
 */
export async function fetchRecentlyEmailed(
  supabase: SupabaseClient,
  candidateIds: string[],
  now: Date,
  windowDays = LEDGER_WINDOW_DAYS,
): Promise<Set<string>> {
  const barred = new Set<string>();
  if (candidateIds.length === 0) return barred;

  const cutoff = new Date(now);
  cutoff.setDate(cutoff.getDate() - windowDays);
  const cutoffISO = cutoff.toISOString();

  const batchSize = 500;
  for (let i = 0; i < candidateIds.length; i += batchSize) {
    const batch = candidateIds.slice(i, i + batchSize);
    const { data, error } = await supabase
      .from("email_send_log")
      .select("user_id")
      .in("user_id", batch)
      .gte("sent_at", cutoffISO);
    if (error) {
      // Fail-CLOSED per-batch: if we cannot prove a user is clear, treat the
      // whole batch as barred rather than risk a double-send / re-earning a pause.
      console.error("[SendLedger] read failed, barring batch:", error.message);
      for (const id of batch) barred.add(id);
      continue;
    }
    for (const row of data || []) barred.add(row.user_id as string);
  }
  return barred;
}

/**
 * Stamp the ledger after a successful send. Best-effort; a failed insert logs
 * but does not fail the email (the distinct-cron-minutes + 6d window make a
 * missed stamp low-risk). Call ONLY on result.success.
 */
export async function logLifecycleSend(
  supabase: SupabaseClient,
  userId: string,
  emailType: LifecycleEmailType,
): Promise<void> {
  const { error } = await supabase
    .from("email_send_log")
    .insert({ user_id: userId, email_type: emailType });
  if (error) console.error(`[SendLedger] insert(${emailType}) failed for ${userId}:`, error.message);
}
```

## De-dupe / frequency-cap guarantees (how collisions are prevented)

1. **Structural disjointness:** weekly/monthly target `active-in-period`; win-back targets `30d-silent`. A user cannot be both → a report and a win-back can never fire in the same run for the same user. No cohort math needed at runtime; it's true by the query predicates.
2. **Ledger cap (belt-and-suspenders):** `email_send_log` + `fetchRecentlyEmailed` enforce **≤1 lifecycle email / rolling 6 days** across weekly∪monthly∪winback. This is what auto-skips the weekly when monthly lands on a Monday (1st-of-month ∩ Mon 09:15/09:20): the monthly run at `:20` stamps `monthly`; that user was in the `:15` weekly run 5 min earlier — order matters, so the monthly's `barred` set will include anyone the weekly stamped, and vice-versa the weekly stamped user is barred at monthly. Because both run same morning, whichever fires *second* sees the ledger row from the first and skips. (Weekly `:15` fires before monthly `:20`, so on that rare Monday the user gets the **weekly**, and the monthly skips them — spec says overlap handled by the 6-day cap; direction is acceptable and honest.)
3. **Ledger fail-closed:** a failed ledger read bars the batch rather than risking a double-send (deliverability > coverage).
4. **Win-back idempotency:** `winback_sent_at` marker ("then stop") independent of the ledger — even if the ledger window rolls off, a second win-back can't fire until the user returns (heartbeat clears it) and re-lapses.
5. **Distinct cron minutes + `MAX_EMAILS_PER_RUN`(100) + 50s/60s timeout guard** all preserved per route.
6. **Master flag OFF by default:** with `LIFECYCLE_EMAILS_ENABLED` unset, all three lifecycle routes no-op — crons can ship to prod dark; **nothing sends until the owner flips the flag and redeploys.** The 14d email is deleted regardless of the flag (it's simply removed from the loop).
7. **Race note (unhardened, acceptable):** ledger check-then-send isn't transactional across runs, but distinct minutes + disjoint cohorts + 6-day window make double-sends effectively impossible. Future hardening: unique index on `(user_id, email_type, date_trunc('week', sent_at))` + `INSERT … ON CONFLICT DO NOTHING`.

# COMPLETENESS CRITIC — What is MISSING to ship safely

The design is thorough on tokens, cadence, and de-dupe. But there are **8 real gaps** between "drafted" and "shippable," 3 of them hard blockers. Ordered by severity.

## BLOCKERS (cannot go live without)

**B1 — No preview/test path exists. This is the single biggest gap.**
Every route is `POST` gated behind `Authorization: Bearer ${CRON_SECRET}` and blasts up to 100 real users. There is **no way to render one email to yourself** before the first real send. You cannot QA "Gmail + Apple Mail + Outlook" (checklist item 13) without one. The whole restyle is unverifiable until a live cron fires at real users.
- **Minimal to-do:** add `?preview=<email>&type=weekly|monthly|winback` (or a tiny `/api/email/preview` route, same-auth) that builds the HTML for one synthetic/real user and either returns the raw HTML (`Content-Type: text/html`) or sends exactly one message to the given address. Ship this **first**, before flipping `LIFECYCLE_EMAILS_ENABLED`. Without it there is no test path at all.

**B2 — Unsubscribe scope is not honest yet (deliverability + trust risk).**
The monthly email's footer + `List-Unsubscribe` both point at `?scope=monthly`, but the live route (verified: `unsubscribe/route.ts`) **ignores `scope` entirely** and always sets `email_digest=false`. So a user who clicks "unsubscribe from monthly highlights" is silently killed off **all** email, and the confirmation page still says *"You won't receive weekly digest emails anymore"* (line 155). That is a dark-pattern-by-accident and a false statement — exactly the kind of thing that re-earns a pause.
- **Minimal to-do:** implement checklist item 10 (`scope=monthly` → flip only `monthly_highlights`; default → `email_digest=false`) **and** fix the two confirmation strings (report-neutral + scope-aware) **before** the monthly ships. This is not optional polish; the monthly's own headers already promise it.

**B3 — Migration is a hard prerequisite and must be applied, not just written.**
`monthly_highlights`, `winback_sent_at`, `email_send_log` do not exist in the DB. The monthly gate, the win-back marker, and the *entire ledger* silently no-op or error until the migration runs. The draft correctly flags this but there's no "applied + verified" step.
- **Minimal to-do:** apply `20260824090000_lifecycle_email.sql` to staging **and prod**, then verify columns/table exist, **before** any cron is allowed to fire. Note: `email_send_log` has **no RLS policy and no `user_id` FK** in the draft — service-role writes work, but add at minimum an FK-or-comment and confirm RLS is intentionally off (service-role bypasses it, so fine, but say so).

## SHOULD-FIX (ship-degrading, not ship-breaking)

**B4 — Metrics (open/click → PostHog) are completely absent.**
The prompt explicitly asks. There is **zero** email telemetry in the codebase today — no open pixel, no click wrapping, no PostHog `capture` on send. You will fly blind: you cannot answer "did the redesign lift re-opens?" or "is the win-back annoying people?" (complaint rate is the deliverability canary). Resend provides open/click webhooks + per-tag analytics; the sends already set `tag` (`weekly`/`monthly`/`winback`), so the data is half-wired.
- **Minimal to-do (pick the cheap tier):** (a) at minimum, `posthog.capture(userId, 'lifecycle_email_sent', {type})` right where `logLifecycleSend` fires — you already have the hook point. (b) For open/click, enable Resend's tracking + add a `/api/email/resend-webhook` that forwards `email.opened`/`email.clicked`/`email.complained` to PostHog keyed by the `category` tag. Opens are lossy (Apple MPP inflates them) but **complaints + clicks are the ones that matter** for the anti-pause thesis. Do not ship the win-back without at least complaint-webhook visibility.

**B5 — Gradual rollout is all-or-nothing.**
`LIFECYCLE_EMAILS_ENABLED` is a single global boolean: OFF → 0 users, ON → up-to-100/run of your entire active base on the first Monday. After an owner-requested pause, blasting the full cohort on flip is the riskiest possible re-entry. There's no canary.
- **Minimal to-do:** add a percentage/allowlist gate. Cheapest: `LIFECYCLE_EMAIL_ROLLOUT_PCT` (0–100) checked via a stable hash of `userId` (`hashInt(userId) % 100 < pct`), or a `LIFECYCLE_EMAIL_ALLOWLIST` of user IDs for the first send. Flip to a handful (owner + a few internal accounts) → verify inbox rendering + unsub → 10% → 100%. Reuses the existing flag file.

**B6 — Locale coverage of *interpolated* strings is unverified (not the static keys).**
The 5-locale static tables are complete and good. But two runtime interpolations are **English-only in the drafts** and will ship English into de/es/fr emails:
- Weekly `heroCapsuleBody` uses `{when}` — the drafts' own implementer note says render via `toLocaleDateString(dateLocale,{weekday:"long"})`, but the digest route must actually pass a **localized** weekday, not `"Thursday"`. Verify the route does this per-recipient-locale, not once in en.
- `roomName` / `trackName` / wing names: these come from DB/`TRACKS` constants. The digest route already resolves track names via `enMessages` (verified line 473 → `enMessages.tracksPanel`) — i.e. **track names are hardcoded English today.** The monthly's SAGE "Preserve" bar will say the English track name to a French user.
- **Minimal to-do:** confirm every `{month}`/`{when}`/`{weekday}` is built with the recipient's `dateLocale`, and decide explicitly whether room/track names stay English (acceptable — they're proper-ish nouns) or get localized. Document the decision; don't leave it as a silent English leak.

**B7 — Frequency-cap storage has an unbounded-growth + no-cleanup gap.**
`email_send_log` is append-only with no retention. `fetchRecentlyEmailed` only ever reads a 6-day window, so 100% of rows older than 6 days are dead weight forever, and the `IN (...)` batch scans get slower over time. Also: the "fail-CLOSED → bar the whole batch" behavior means a **transient Supabase read blip silently suppresses that week's entire cohort** with only a `console.error` — no alert, and it looks identical to "nobody was eligible."
- **Minimal to-do:** (a) add a cleanup — either a `DELETE FROM email_send_log WHERE sent_at < now()-interval '30 days'` at the top of one cron, or a partial index; trivially cheap. (b) On fail-closed batch-bar, surface it (return a `ledgerReadFailures` count in the JSON so a monitor/owner sees "0 sent because ledger was down," not a silent quiet week).

## MINOR (note, don't block)

**B8 — Monthly-vs-weekly overlap direction is correct but the ledger race is real on the collision Monday.**
The draft's own analysis is honest: weekly `:15` stamps before monthly `:20`, so on a 1st-of-month-Monday the user gets the **weekly** and the monthly skips — the *richer* retrospective is the one dropped, which is the opposite of the spec's stated preference ("don't deny your best users the retrospective"). It's acceptable and self-documented, but if the owner cares, swap the cron minutes (monthly `:15`, weekly `:20`) so monthly wins the collision. One-line change. Also: `fetchRecentlyEmailed` check-then-insert is non-transactional — fine at these volumes, but the drafted `ON CONFLICT` unique key is the real fix if volume grows; leave it as documented future-hardening.
